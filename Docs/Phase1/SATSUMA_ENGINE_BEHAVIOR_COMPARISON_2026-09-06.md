# Satsuma: поведение двигателя против замороженного оригинала

Дата: 2026-09-06, повторный аудит после ручного запуска пользователем.
Статус: **Read-only behavioral audit / ImplementationPartial / RequiresCalibration**.
Это отчёт о текущей реализации, не исправление кода и не подтверждение полной
паритетности. Область: штатный двигатель Satsuma, его настройка, запуск,
холостой ход, топливоподача, последствия неисправностей и обратная связь.
Это не аудит всей игры и не разрешение на Phase 2.

## 2. Подтверждённые отличия и недостающие связи

### A. Хлопки сейчас слишком регулярны и не сохраняют донорские условия

Текущий `SatsumaEngineSymptomAudio.Tick` накапливает для впуска/выпуска
`RPM / 60 / 24 * severity` и играет импульс по достижении единицы.
При +5 градусов severity равен .7 постоянно. Например, при 1800 RPM получается
примерно один хлопок каждые **1.143 s**, даже на совершенно постоянных оборотах.

В доступной ветке Spitting111114 сначала требуется рост более чем на **250 RPM**
внутри окна 1 s, затем проверяется `Valves.MotorSpit` либо `Cylinders.Spitting`.
После звука выполняется случайная пауза **2–5 s**. Backfires111113 отдельно
проверяет падение более чем на 150 RPM и `Mixture.Blow`; после выпускного звука
пауза 1–6 s. Для ошибочной фазы есть отдельный `TIMINGBACKFIRE`.

Следовательно, нынешнее отличие — не только фиксированный вместо случайного
интервал: потеряны условия изменения оборотов. Подмена «хлопков иногда» простым
добавлением случайного таймера этого не исправит.

Кроме того, бедная смесь и раннее зажигание у нас объединены через `Max` в
`Knock01` и один непрерывный pinging-слой. В доноре ранний угол активирует
SoundPinging, а `Mixture.Blow` обслуживается отдельной выпускной цепочкой.
Нынешний `ExhaustBackfire01` зависит только от отрицательной ошибки распредвала:
бедная смесь сама этот выход не выставляет.

Ограничение вывода: у Backfires есть состояния Check temp / Knocking? / Knock,
но локальный startState — Low fuel; входящий переход в Check temp и глобальные
переходы не найдены. Нельзя выдавать присутствующий там порог 100 C за доказанное
обязательное поведение без отдельной проверки внешнего входа.

### B. Нет отдельных событий пропуска воспламенения

Модель использует число пригодных цилиндров и постоянные коэффициенты:
ошибка фазы вычитает одну четверть вклада, плохие свечи уменьшают общий момент
до 30% через roughness. В доноре есть отдельные ветки `Random / Misfire` по
цилиндрам и изменение их вклада в расчёт. Сейчас нет соответствующей истории
пропусков: нерегулярные импульсы момента, неровные обороты и звуковой импульс
не происходят из одного события горения. Исправная тихая работа моделируется;
полноценное промежуточное «троит/иногда хлопает» — ещё нет.

### C. Смесь перенесена не целиком; её границы требуют проверки на новом solver

Перенесены температурная плотность, фактор подсоса `1 + choke`, предел 22,
AFR-масштаб, пороги 12.7 / 14.05 / 16 и донорские изменения power/torque.
Это не произвольные вновь придуманные пороги.

Однако код называет выбранное значение средним донорского случайного интервала,
но ограничение применяется **после** усреднения. У донора ограничивается каждый
результат. На нулевом газе:

- donor: `E[min(14 + U(0,1.8), 15)] = 14.722222...`;
- сейчас: `min(14 + (0+1.8)/2, 15) = 14.9`.

Сейчас выходит примерно на 1.21% беднее истинного среднего; исчезает и само
изменение смеси между пересчётами. Вблизи границы это существенно, хотя само
по себе не объясняет всю остановку двигателя.

Пороговые скачки тоже реальны. Пример: 80 C, без подсоса, исправные клапаны,
угол зажигания 15, холостой диапазон оборотов:

| Настройка винта | AFR | Коэффициент момента |
| ---: | ---: | ---: |
| 13.4 | 16.184 | .827 |
| 13.6 | 15.946 | 1.000 |
| 15.4 | 14.082 | 1.000 |
| 15.6 | 13.901 | 1.093 |
| 17.0 | 12.757 | 1.227 |
| 17.2 | 12.608 | .775 |
| 22.0 | 9.857 | .893 |

То есть соседний шаг 17.0 -> 17.2 меняет коэффициент примерно на -37%.
Это следствие перенесённых кусочных формул, а не доказательство опечатки в
арифметике. Их ощущение в новой динамике не проверено сравнительной ездой.
Просто сгладить всё «для удобства» означало бы отдельное решение о калибровке,
а не точный перенос оригинала.

Важно: донорские проверки AFR<8 -> Off и AFR<10 -> Sputter **отключены**.
Их нельзя включать под видом восстановления паритета. В текущем допустимом
диапазоне настройки минимальный mixture около .616, так что проверка
`mixture > .5` сама по себе не даёт запрета запуска для очень богатой смеси.

### D. Запуск, холостой и остановка остаются на предварительной динамике

Канонический Satsuma prefab действительно ссылается на
`Assets/Game/Vehicle/Content/Simulation/Configurations/M06_VehicleSimulationConfig.asset`
(GUID `6cd2f307cfe1ac2449cae781607f19c5`). Это не только неиспользуемый пример.
Config прямо маркирован `ProvisionalProjectTuning`: кривая момента,
инерция .24, стартер 65 Nm / до 650 RPM, порог запуска 450 RPM,
остановка ниже 500 RPM в течение .28 s, redline 7000.

SatsumaOperatingModel расширяет его, но не заменяет регулятор холостого:
`0.14 + idleError / max(400,idleTarget) * .55`. У донора Drivetrain другая
форма момента/трения/поддержки оборотов; Starter.Fuel Mixture удерживает
заданные 300 RPM, а Running проверяет выключение ниже 100 RPM.
Числа нельзя менять по одному без проверки совместной динамики.

Температурная задержка `(100-T)/20` у нас ограничена .5–8 s и привязана к
накопленному времени прокрутки. Полный подсос меняет смесь и целевые обороты,
но непосредственно эту задержку не сокращает. В доноре это начальное ожидание
Mixture.State 2, а топливная готовность ещё проходит через FuelLine/CarbReserve.

При достаточных формальных условиях мотор объявляется Running по 450 RPM,
даже если полученный момент не сможет поддерживать холостой. В численном
пересчёте крайне бедная смесь при удержанном ключе вызывает повторные
Running -> Stalled -> Cranking -> Running. Это кандидат для отдельного реального
регрессионного сценария, не новый выполненный Unity-тест.

### E. Топливная часть существенно неполна

`FluidSimulation.Step` одинаково для Satsuma и generic-пути расходует бензин
через интерполяцию .00035–.0025 L/s по сглаженной педали газа. Ни AFR/подсос,
ни RPM туда не входят. При одинаковой педали богатая и бедная смесь расходуют
одинаковое количество бензина.

У донора Mixture.Wait 2 передаёт `AFR * 30000` в FuelLine. Fuel Usage использует
RPM / ограниченный Consumption, газ, состояние бензонасоса и CarbReserve.
Проверены отдельные пределы резерва 0..0.1 и готовности около .095;
точный новый SI-профиль должен включать всю цепочку, а не перенос одной цифры.

Сейчас отсутствуют соответствующая топливная камера/её заполнение и истощение,
производительность/износ насоса, накопление загрязнения карба без воздушного
фильтра. `SatsumaFuelLineConnection` прямо реализует только болт и сохранение:
утечка через незатянутую магистраль пока не подключена. Отдельный ранее
сообщённый баг заправки этим аудитом не воспроизводился и не исправлялся.

### F. Сервис и износ есть, но это ещё не полная цепь последствий оригинала

Уже реализованы раздельные жидкости, конечный объём, крышки/заливка, давление,
утечки ряда уплотнений, загрязнение масла, ускоренный износ при недостатке
масла/перегреве, работа электрического вентилятора и ременная передача.
Пустое масло/охлаждение теперь не являются мгновенным магическим запретом пуска.

Остаются различия и пробелы:

- тепло считается по собственным коэффициентам нагрузки, масла и knock;
  донорская связь смеси с Rate и её дальнейшими тепловыми расчётами не целиком
  воспроизведена;
- нет полного прогрессирования износа генератора, стартера, бензонасоса и
  свечей от работающего двигателя/смеси; не следует принимать сериализованный
  default condition за реально действующий износ;
- плохая прокладка сейчас учитывается в утечках, но не воспроизводит донорскую
  отдельную потерю цилиндрового вклада и полный набор симптомов;
- дым изношенных поршней, пар/прочие видимые последствия и связанные цепочки
  отказа в текущих исследованных engine-представителях отсутствуют;
- состав впуска/выпуска меняет звук, но не передаётся в operating inputs для
  изменения мощности, как в донорских ветках Valves;
- заряд аккумулятора остаётся автомобилевым состоянием; замена купленного
  аккумулятора и зарядное устройство не объявляются этим пакетом завершёнными.

## 3. Что действительно уже работает и сохраняется

Сборка и проводка имеют отдельные условия прокрутки и горения; запас бензина
реален. Настройки карба, распределителя, фаз, клапанов и генератора потребляются
действующей симуляцией, а не только крутят меши. Подсос меняет смесь/холостой.
Аккумулятор запускает, исправно подключённый генератор может поддерживать уже
работающий двигатель. Жидкости, износ и настройки имеют существующих владельцев
и отдельные save-расширения. Движение механики и звук отделены от физики монтажа.

Ранее выполненные итоговые проверки: 1359 EditMode, 127 PlayMode и 3 Bootstrap
успешных случаев, 4 явно пропущенных; точные фильтры и ограничения находятся в
`SATSUMA_LIVE_ENGINE_INTEGRATION_2026-09-06.md`. Они доказывают проверенные
инварианты/потоки, **не** полноту донорского поведения.
Текущий аудит не повторял эти прогоны.

## 4. Отдельно: метки распредвала и нынешнее управление

`AssemblyCamshaftTimingState` хранит +5 в новом снимке; operating model ждёт
ноль с допуском 1 градус. +5 даёт потерю четверти цилиндрового вклада и
`IntakeSpit01=.7` независимо от правильности карба.

Существующее управление соответствует ранее разобранному донорскому механизму:

1. Шестерня установлена, центральный болт затянут до stage 8, цепь отсутствует,
   доступ не закрыт препятствующими деталями.
2. Ключ **10 mm**, дополнительный скролл **вверх**: +5 градусов, подсказка
   «ВЫСТАВИТЬ МЕТКУ». Сам болт остаётся stage 8.
3. Скролл **вниз** ослабляет болт, а не возвращает фазу на -5.

Не следует обещать пользователю «один щелчок вниз». Точную экранную сторону
поворота и совпадение двух видимых меток этот read-only аудит не наблюдал;
запрошен скрин. Совпадение видимых меток с логическим нулём пока не подтверждено
отдельным графическим тестом.

Есть дополнительный риск интерпретации изображения после запуска:
`SatsumaEngineMechanicalMotion` добавляет к настройке отдельную вращательную
фазу, сохраняет её после остановки и при снятии цепи; сброс выполняется при
ResetPresentation/restore. Поэтому текущий видимый поворот шестерни после
прокрутки не равен одному только сохранённому углу регулировки.
Это подтверждённый порядок композиции, но не доказательство того, что именно
он вызвал пользовательскую ошибку при первоначальной сборке.

Дополнительно live-поворот хранится quaternion, а save — только Euler X;
развёрнутые 0..360 и Euler X не тождественны. Это задокументированная адаптация
донорского механизма, не вновь установленная ошибка на +5. Ремонт такой границы
требует отдельного compatibility-решения, а не скрытого изменения DTO.

## 6. Уточнение предложенной пользователем логики

Три режима подходят как описание ощущения игрока, но не как три жёстких
симметричных диапазона вокруг единственного «идеального щелчка»:

1. **Устойчивая работа:** диапазон допустимой настройки. Небольшое обогащение
   может изменить тягу/расход, не требуя хлопков. Оптимум зависит от режима,
   температуры и подсоса, а не от одной цифры на винте.
2. **Неустойчивая работа:** заметное отклонение/неисправность; пропуски,
   провалы тяги и обусловленные событиями хлопки. Детонацию, хлопок впуска,
   хлопок выпуска и механический стук следует различать по причине.
3. **Не поддерживает работу:** смеси/искры/подачи или момента недостаточно —
   не схватывает либо глохнет. Но нельзя обещать, что любая максимально богатая
   настройка обязательно глушит оригинальную игру: её соответствующие hard-veto
   действия отключены.

Фазы/распределитель/клапаны проверяются отдельно: нормальная смесь не должна
«исцелять» неправильную метку. Число настройки карба не равно показанию AFR.

## 7. Следующий ровно один пакет

**11A-V1: калибровка stock engine и причинной обратной связи.** Начать с
согласования видимых меток и логического угла, затем проверить одинаковые
сценарии исправного/неисправного пуска, холостого и изменения газа на исходных
донорских условиях. Устранить потерянные условия хлопков и добавить реальные
проверки переходов «схватил -> удерживает / заглох», включая удержанный ключ.
Новый Satsuma-профиль должен опираться на существующий модуль, не менять M06
глобально. Изменение намеренно сохранённой границы save/angle — только после
минимального compatibility-предложения.

Для приёмки нужны одинаковые состояния: холодный/прогретый, подсос 0/часть/1,
шаги смеси вокруг каждого порога, правильные и неправильные фазы/искры,
удержание холостого, набор/сброс газа, нагрузка сцеплением и сохранение/загрузка.
Сравнивать RPM(t), AFR(t), состояние горения, моменты/количество звуков и расход.
Где нет исполнимого capture locked-донора — явно оставлять источник как
статический behavioral evidence, а результат как RequiresCalibration.

Это рекомендация, не неявное разрешение начать исправления. Код, prefab,
config, пользовательские saves, 00–08A API и UI этим отчётом не изменены;
миграции не добавлены. Создан только этот проектный отчёт.
